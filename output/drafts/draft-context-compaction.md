## 开头（钩子）

你有没有遇到过这种情况：让编码代理连续干了一下午活，突然它告诉你"Request exceeds the maximum size"——上下文窗口满了。任务没做完，历史却塞不下。

你有两个选择：开新会话（把这一下午的判断、决策、未完成的工作全部丢掉），或者——压缩。

这篇文章讲的就是后者：上下文压缩（compaction）到底是怎么工作的，为什么它不是"简单裁掉一半历史"，以及它和 prompt cache、token 账单之间的微妙关系。

---

## 一、上下文为什么会溢出

编码代理会话的每次请求，都包含四样东西：

1. 系统提示（你是谁、怎么干活）
2. 已加载的文件（AGENTS.md、CLAUDE.md 这类规则文件）
3. 工具定义
4. **完整的历史对话**——每一轮"助理调用工具 → 工具返回结果 → 助理继续"都在加长这段历史

LLM 只能"看见"上下文窗口内的输入。窗口有限，历史无限增长，迟早溢出。注意一个反直觉的事实：**输出质量会随着上下文变长而下降**（context rot）——窗口塞满时，早期的关键约束会被遗忘。所以问题不只是"装不下"，还有"装得下但不记得"。

## 二、压缩不是什么

最直觉的方案是"确定性裁剪"：保留最近 N 条，把更早的丢掉。

但通行实现不是这样——**压缩是一次 LLM 请求**。

把旧历史提取出来、序列化，然后发给一个独立的模型调用，让它把这段历史总结成一份"换班简报"式的结构化摘要。再用这份摘要替换旧历史，为后续消息腾出空间。

为什么用模型而不是直接裁？因为直接裁是"硬断片"——中间决策、关键约束、未完成工作的状态会整个丢失；而摘要能保留这些信息的压缩形态。代价是：**压缩是一次额外的 LLM 调用**，有成本，但通常比继续累积几千行原始工具输出便宜得多。

## 三、Pi 的 compaction 实现：一个具体例子

以 Pi 框架为例（OpenClaw 的最初引擎，源码与官方文档都公开），看实现细节：

### 触发时机

- **自动**：上下文规模接近窗口上限时触发；自动压缩在**回合结束之后**检查——因为回合内每个请求都在复用同一段 prompt 前缀，可以命中 prompt cache；如果回合中途直接碰到溢出错误，也会在中途压缩。
- **手动**：`/compact` 随时触发。

### 保留策略

压缩时**保留最近若干条消息原样不动**，只压缩更早的历史。保留量由可配置的 token budget 决定，Pi 默认约 2 万 token——大约相当于最近 5~20 轮对话。这保证了"手头正在做的事"不被打断。

### 独立的压缩请求

压缩请求与普通对话有三点不同：

1. 系统提示不同：不再是"你是专家编码助手"，而是"**你是上下文摘要助手**"。
2. 用户消息不同：要求输出"这个会话分支的结构化摘要，供稍后返回时恢复上下文"，并明确指定分节——**目标（goal）、进展（progress）、关键决策（key decisions）**。
3. 它是独立请求，**不携带既有历史**——因此可以用不同的、更便宜的模型来做压缩，不产生额外成本。

压缩后的上下文结构长这样：

    [system][tools][summary][最近几轮][新用户消息]

### 可移植性

摘要以**纯文本**存进会话。这意味着它可读、可移植——在 Pi 里切换模型后，这份摘要依然能用。这是"压缩表示"与"原始历史"的关键区别：原始历史绑定模型行为，摘要只绑定事实。

## 四、隐藏的账单：压缩 vs Prompt Cache

这里有个大多数人不注意的细节。

Prompt caching 让同一会话的重复请求更便宜，前提是**前缀精确匹配**。压缩改变了保留轮次的前缀——那些轮次的内容没变，却不再命中之前的缓存，需要重新计算。也就是说：

**压缩的瞬间会有一笔"缓存重建"成本；但压缩后的新请求会从新前缀开始重新建立缓存，后续继续受益。**

所以压缩不是免费的，它是"用一次模型调用 + 一次缓存失效，换后续大量空间的持续可用"。

## 五、放到更大图景里看

Claude Code 的模型与努力（model vs effort）文档给出了更宏观的 token 管理视角：

- **模型**决定每个输出 token 的单价；**努力**决定生成多少 token。压缩属于"努力"侧的机制——它控制的是会话生命周期的总 token 消耗。
- 循环（loops）的官方建议里有一条：**"大规模跑之前先小切片试跑，动态工作流可能生成上百个代理"**——而每个长会话都可能走到压缩这一步。理解压缩 = 理解长任务的真实成本结构。
- 一个工程化的旁证：Pi 的 pi-hypa 扩展用钩子直接清理 bash 输出，token 削减 80%~98%——压缩是"事后兜底"，主动控量是"事前省钱"，两者配合才完整。

## 结尾（金句位）

上下文窗口是硬的，会话是软的。压缩的本质，是把"窗口装不下的历史"变成"模型读得懂的记忆"——一次独立的 LLM 请求，一份可移植的纯文本摘要，一笔缓存重建的账。理解了它，你就理解了为什么长会话不会爆掉：不是窗口变大了，而是代理学会了"换班"。
