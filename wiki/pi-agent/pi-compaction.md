## 摘要

LLM 的上下文窗口有限，而编码代理会话的输入（系统提示、AGENTS.md、工具定义、历史消息与工具调用结果）会随工作持续膨胀，最终超出窗口返回 `Request exceeds the maximum size`。Pi 的解法是 compaction：用一次**独立的 LLM 请求**把历史总结成换班简报式的结构化摘要，替换旧历史、保留近期轮次，让会话得以继续。Pi 默认保留约 2 万 token 的近期上下文（约 5~20 轮），可在回合结束后自动触发或 `/compact` 手动触发；摘要以纯文本存入会话，跨模型可移植。代价是 compaction 会打破 prompt cache（缓存要求前缀精确匹配），但之后的请求会重新享受缓存。

---

## 要点

- 上下文溢出时只有两条路：开新会话（丢弃历史，且输出质量随上下文增长而下降——context rot），或压缩（compaction）——用更小的表示保留会话。
- Compaction 的通行实现不是确定性裁剪函数，而是一次 LLM 摘要请求：把部分历史替换为压缩表示，为后续消息腾出空间。
- Pi 在回合结束后检查自动压缩（此前每个请求都能复用缓存前缀）；遇上下文溢出错误时也会在回合中途压缩。
- Pi 保留最近若干条消息不压缩，保留量由可配置的 token budget 决定，默认 2 万 token ≈ 5~20 轮。
- 压缩请求是**独立请求**：换用"你是上下文摘要助手"的系统提示，要求输出含目标（goal）、进展（progress）、关键决策（key decisions）的结构化摘要；因不携带历史，可以用不同的（更便宜的）模型。
- 摘要以纯文本作为 compaction entry 追加进会话——可读、可移植，切换模型后摘要仍可用。
- 压缩会打破 prompt cache：保留的轮次 token 虽相同，但前缀变了，必须重新计算；压缩后的新请求会再次建立缓存。
- Pi 的压缩可被扩展替换：可以写一个带自定义压缩提示词的扩展来做实验。

---

## 详细内容

### 上下文为何会溢出

LLM 只能"看见"上下文窗口内的输入。编码代理会话的每次请求都包含：系统提示、已加载文件（如 AGENTS.md）、工具定义，以及**完整的历史对话**。每一轮（assistant 工具调用 → 工具结果 → assistant 回复）都在加长这段历史，直到超过窗口上限，模型拒绝请求。

### Compaction 是什么

面对溢出有两种选择：

1. **开新会话**：丢掉全部积累的上下文（包括既有决策和未完成工作）。有时这不失为明智之举，因为已有研究表明 LLM 输出质量随上下文增长而下降（context rot）。
2. **压缩**：为会话生成一个更小的表示，让同一段会话继续下去。这就是 compaction。

理论上压缩可以是确定性函数（保留一部分、丢弃其余），但实践中通行做法是**用一次 LLM 请求来总结历史**：把部分历史替换为压缩表示，腾出空间容纳新消息和新工具调用。

### Pi 的实现

- **触发时机**：当上下文规模接近窗口上限时自动触发；也可 `/compact` 手动触发。自动压缩在**回合结束之后**检查——回合内每个请求都在扩展同一段 prompt，可复用已缓存的精确前缀；若回合中途遇到上下文溢出错误，Pi 也会在回合中途压缩。
- **保留策略**：压缩时保留最近若干条消息原样不动，之前的消息被提取、序列化后交给摘要。保留数量不固定，取决于可配置的 token budget；默认 2 万 token，约合 5~20 轮。
- **独立的压缩请求**：压缩请求与常规对话请求有三点不同：
  1. 系统提示不同——不再是"你是专家编码助手"，而是"**你是上下文摘要助手**"；
  2. 用户消息不同——要求输出"这个会话分支的结构化摘要，供稍后返回时恢复上下文"，明确指定**目标、进展、关键决策**等分节；
  3. 它是独立请求，不携带既有历史——因此可以用**不同的模型**来压缩，不会产生额外不必要的成本。
- **结果处理**：摘要作为 compaction entry 追加进会话，会话继续。压缩后的上下文形如 `[system][tools][summary][recent turns][new user message]`，为后续消息腾出大量空间。
- **可移植性**：摘要以**纯文本**存于会话中，保持压缩后上下文可读、可移植——在 Pi 中切换模型后仍可继续使用这份摘要。

### Compaction 与 Prompt Caching

Prompt caching 让同一会话中的重复请求更便宜，但前提是**前缀精确匹配**。压缩改变了保留轮次的前缀：那些轮次的 token 内容没变，却不再命中之前的缓存，需要重新计算。压缩后的新请求则会从新的前缀开始重新建立缓存，后续继续受益。

### 可替换性

Pi 的压缩实现本身也可被扩展替换——写一个带自定义压缩提示词的扩展，即可实验不同的压缩机制。这正是 Pi "一切皆可扩展"设计哲学的又一例证。
