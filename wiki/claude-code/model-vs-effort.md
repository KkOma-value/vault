## 摘要

Claude Code 有两个都能“改善答案”的设置：模型（model）和努力程度（effort）。模型决定 Claude **知道多少**——用哪一组冻结的权重处理请求；努力程度决定 Claude 为一个任务**做多少工作**——读多少文件、验证多少、在向你确认前完成多少多步骤任务。当结果不满意时，先检查上下文（prompt、工具、skills、验证方式），再判断：是它**不够聪明**（换更大模型）还是**不够努力**（提高努力程度）。

---

## 要点

- 更大的模型在行业基准上性能更强，但“思考时间”只是总工作量的一部分。
- 模型设置切换的是一组**只读、冻结的权重**；请求不会改变权重，上下文只是“引导”而非“训练”。
- 幻觉是权重按训练模式生成了看似合理的 token 序列，而不是“查找失败”。
- 模型决定每个输出 token 的成本，但不决定**生成多少 token**——那由努力程度控制。
- Thinking、tool calls、给用户的文本都是同一个循环产出的普通 output token，同价计费，且会留在本轮上下文里。
- 努力程度作为请求的一部分发给模型，模型被训练过在每个努力档位下的行为；它设定 Claude 认为任务“完成”前需要多彻底、多确定。
- 高努力更倾向复核（验证答案、排查本可跳过的假设），但不会在简单任务上人为膨胀用量；“过度思考”是训练时专门盯防的退化。
- 多数任务用**模型默认努力档**即可；把努力当作对“快 vs 彻底”的手动覆盖，按领域/工作类型的总体偏好来设，而非逐任务调节。

## 详细内容

### 模型选择如何运作

按下回车后，Claude Code 把你的消息、系统提示、工具定义、CLAUDE.md、对话历史和上下文中的文件打包成**单个 API 请求**。服务器端先分词：文本被切成片段，每片映射到固定词汇表中的一个整数（如 `const`→1978，`await`→4293），于是提示变成一个整数数组。

模型的任务是读取数组并预测下一个 token：为词汇表中每个 token 计算概率并选取。这靠权重（参数）实现——数十亿个数字组成的大型矩阵，输入经过一系列矩阵乘法后在末端读出概率。**权重包含模型“知道”的一切**，训练时设定，推理时只读。所谓“推理”就是用权重固定的模型做前向计算。

因此改变模型 = **切换用哪一组冻结权重**处理请求，同时也改变每个 output token 的成本；但它不决定生成多少 token。

模型不会一次生成完整答案：预测一个 token，追加到序列，再重跑整个计算得下一个。200 个 token 的响应需要 200 次权重迭代——这是大部分等待时间和输出成本的来源。

### 努力程度如何运作

努力档位随 prompt 一起发给模型；模型被训练理解各档位的行为，这种行为编码在冻结权重里。努力设定的是 Claude 在认为任务完成前需要多**彻底**、多**确定**，每一轮都会权衡，更高的确定性需要更多 token 才能达到（示意图中高努力路径约多产生 7 倍 token）。

高努力时 Claude 常先建计划，努力档影响计划的深度与广度；但计划不是固化的——拿到行动结果后，它会更新对进度和结果确定性的判断。比如三假设调试计划在第 1 步就找到 bug，就会明说“第一步已找到，其余无需检查”并跳过（表现为任务列表在运行中被修订）。

### 结果错了该改什么

第一反应不应是改设置，而是看你给的**上下文**：prompt 是否太模糊？是否连了对的工具？有没有对的 skills？若在本不需要高努力的任务上加努力，修复通常在上游（context / CLAUDE.md / 任务拆分）。

给了清晰上下文仍出错时，问自己：**是不够努力，还是不够懂？**

- **模型问题（问题太难）**：微妙 bug、陌生领域、架构决策，或小模型无论给多少上下文都自信地错——换更大模型。大模型也更擅长处理模糊；小模型上，具体、指令式的引导更易成功。例行工作（能精确描述的编辑、机械改动、已在上下文里的代码问题）用小模型即可，没必要为用不到的能力付费。
- **努力问题（不够努力）**：跳过某个文件、没跑测试、没复核——提高努力档，尤其当你之前把努力设在默认档以下时。

### 专家类比

Fable 是“几乎没人能处理的问题”才请的专才，Opus 是专家，Sonnet 是很强的通才；努力档决定他们各自花多少时间。

- Opus 低努力 ≈ 和资深专家聊五分钟：带来代码库里没有的经验（见过的模式、要检查的坑），但只能快速扫代码而非逐文件细读。
- Sonnet 高努力 ≈ 通才用一整个下午：会读完所有东西、运行、复核，最终彻底理解你的具体代码。
- Fable ≈ 别人都卡住时才叫的专才，即便低努力也能看出别人看不到的东西——这份识别力也是最贵的，值得留给真正需要的任务。

没有谁“普遍更好”：模型 ≈ **多有能力**，努力 ≈ **多彻底**，多数真实任务两者都要一些。

### 努力、模型与 token 消耗的相互作用

- 例行工作、相同努力档：大小模型通常都对。大模型因额外验证步骤消耗更多 token，且单价更高——所以例行阶段降到小模型能实打实省钱且不损质量。
- 更难的多步工作：等式反转。小模型要逼近能力上限、消耗大量迭代，大模型用更少步骤达到同样质量。单价虽高，但在真正吃力的任务上总成本反而可能更低；更重要的是，大模型能完成小模型在任何努力档都做不到的任务。Fable 在长多步工作上领先最明显——测试中它完成了 Opus 与 Sonnet 任何努力档都到不了的任务，也因此单价最高。
- 关键：努力决定 Claude **愿意沿曲线走多远**，不代表它真需要走那么远才完成任务。
- 努力**塑造**但不**限制** token 消耗。系统里唯一硬上限是 `max_tokens`（触顶会中途截断，是钝器，主要与 API 开发者相关）。task budgets、在 prompt 里让 Claude 简短作答等是软控制——模型被训练去遵循（接近上限时会收尾），而非撞上的墙。

一句话：**努力改变 Claude 做多少工作，模型改变 Claude 知道什么。** 不满意结果时先查上下文（清晰 prompt + 对的工具/skills + 可自我验证的方式）；仍错就问：不够懂（模型问题）还是不够努力（努力问题）。

> Opus 4.8 实践注记：测试中，Opus 4.8 默认努力档在同一任务上用与 Opus 4.7 默认档大致相同的 token，产出更好的结果。
